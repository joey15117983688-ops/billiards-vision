# 赛场实时视频：前期准备

更新日期：2026-10-19。

目标是让实时输入具有可验证的连续性、时效和几何定位，再调整球与进球识别精度。当前主界面仍使用本地视频；本次新增独立基础模块和只读诊断入口，没有接入未知赛场地址，没有修改用户校准记录。

## 已完成的基础

| 部分 | 当前实现 | 作用 |
| --- | --- | --- |
| 拉流 | `src/live_source.py`，OpenCV FFmpeg，RTSP/HTTP 系列地址入口 | 独立读流，不阻塞界面线程；真实赛场协议待验证 |
| 有界缓存 | 最多一帧待消费，新帧覆盖旧帧，帧只交付一次 | 处理慢时不形成越来越长的应用队列 |
| 时钟 | 解码收到时的单调时间、帧序号、连接会话编号 | 识别接收间断、重复消费和重连，不再假定“帧号 / 固定 FPS” |
| 断线 | 打开/读取超时、有限退避重连，断线清除待消费帧 | 不把断线当作文件结束，不回到第一帧继续判球 |
| 固定身份 | 独立的球房/球桌/摄像机 ID，生成稳定的校准键 | 地址、密码、临时令牌变化不会改变该摄像机的身份；主界面后续接线时使用 |
| 质量和连续性 | `src/live_readiness.py` | 测量亮度、清晰度、过暗/高亮比例、接收到消费的帧龄、丢帧及分辨率变化 |
| 判定许可 | 校准未就绪、画面过期、异常亮度、重连或长间断时不允许提交事件 | 这是前置许可，不代表已经识别出球或确认进球 |
| 诊断 | `scripts/probe_live_stream.py`，支持本地模拟和网络视频，只读 JSONL | 上赛场前先查看输入和对齐是否可靠，不写入比分或校准 |

网络地址不进入自有诊断 JSON 或异常文本；第三方解码器自身的 stderr 仍应在部署时检查脱敏。凭据通过环境变量提供。

## 准确率要分开处理

1. **输入质量**：在真实机位测量台球像素大小、快速击球拖影、曝光变化、反光和遮挡。依照这些实测值调整机位、照明、分辨率、快门、帧率和编码，而非只提高模型置信度阈值。
2. **几何位置**：每个固定摄像机使用自己的校准基准。继续使用已有参考画面对齐，蓝框、袋口和考题绑定球桌坐标；明显换机位、分辨率变化或对齐失败时暂停坐标和进球结论，重新确认工作几何。
3. **目标身份与连续性**：多帧关联白球、黑球和同色球，恢复跟踪时检查身份。断流、遮挡和漏检不能直接解释为进球；缺失轨迹不画成实测轨迹。
4. **进球证据**：结合真实观测到的运动方向、进入已校准袋口的路径、随后复核等现有规则。状态必须允许“证据不足”。重连后清理像素跟踪连续性，保留已确认比分，并重新积累足够观测；不能跨断线直接补一个进球。
5. **实地复测**：将同一段原始输入、时间信息、人工事件标记和系统输出对应起来，分别测定位误差、漏检、误检、轨迹断裂、进球漏报/误报及处理耗时，不用一个总“准确率”掩盖问题。

## 主程序后续接入位置

```text
摄像机 → 独立拉流 → 帧序号 / 接收时间 / 会话编号
                       ↓
                  有界最新帧交付
                       ↓
              输入质量检查 + 参考画面对齐
                       ↓
             快速球观测 / 身份关联 / 轨迹
                       ↓
              多帧袋口事件复核 → 事件记录
                       ↓
              视频、袋口、考题同步显示

慢速 YOLO：独立处理最新请求；不得形成帧任务积压。
```

- 拆开 `MainWindow.next_frame()` 中本地文件 EOF/重播逻辑和逐帧识别逻辑，网络输入使用另一种来源适配器。
- 将 `observe_current_pot_frame()` 的 `CAP_PROP_POS_FRAMES / CAP_PROP_FPS` 改为流接收时钟；若源 PTS 可靠，再建立源时间到接收时间的映射。
- `CalibrationWorker` 的重新打开文件/seek 行为改为使用当前完整帧快照；实时输入不能 seek。
- 使用会话编号使过期异步推理结果失效，接入重连恢复规则与独立摄像机校准键。
- 轻量的运动/袋口观测优先于慢速模型，跟踪丢帧情况单独计量。如果设备处理能力无法覆盖快速球所需观测频率，降低无关显示开销、增加处理资源或调整输入；丢帧保持低延迟不会自动提高识别准确率。

以上主界面接线尚未实施。前期 `can_commit_event` 也尚未接到主程序比分引擎，不能声称当前桌面版本已经具备完整断流保护。

## 诊断使用

先用本地视频模拟实时输入，同时模拟识别耗时：

```bash
.venv/bin/python scripts/probe_live_stream.py \
  --camera-id '测试球房/1号桌/机位1' \
  --video data/test.mp4 --duration 30 --consumer-ms 100 \
  --output logs/live_preflight/replay.jsonl
```

接入真实地址时，先在环境变量 `VIDEO_STREAM_URL` 中配置地址，再运行：

```bash
.venv/bin/python scripts/probe_live_stream.py \
  --camera-id '实际球房/1号桌/机位1' \
  --stream-env VIDEO_STREAM_URL --duration 60 \
  --output logs/live_preflight/venue.jsonl
```

可加 `--calibration /绝对路径/现有记录.auto.json` 只读验证参考画面对齐。若校准是旧记录且缺少参考图，诊断会保守地显示 `geometry_not_ready`，不偷偷重新校准。该工具不确认进球、不保存视频。默认没有清晰度硬阈值：先测真实机位分布，再配置，避免把纹理少的正常绿色台面误判为模糊。

## 目前能确认与不能确认的内容

- 已测试慢消费者覆盖旧帧、过期帧、重复消费、断线恢复、身份稳定、分辨率变化、异常亮度、可配置模糊门限，以及未恢复连续性时禁止提交事件。
- 已通过本机 HTTP MJPEG 服务，走真实 OpenCV FFmpeg 网络解码；报告在 `logs/performance/live_http_loopback.json`。
- 当前 3 秒本地模拟实测：收到 92 帧，消费 28 帧，覆盖旧帧 63 次，待消费缓存最多一帧。原始诊断在 `logs/performance/live_preflight_replay.jsonl`。这个测试只证明应用队列有界，不代表赛场识别准确率。
- `receive_to_consume_ms` 是**本机收到解码帧到分析的时间**。它无法测出摄像机、NVR、编码器或网络中已经发生的延迟；真正端到端延迟需要现场时间对照/可靠源时间戳。上游长缓存、转播分段和反复发送的冻结画面也不能仅靠最新帧队列排除。
- 目前未连接真实 RTSP、NVR、HLS、WebRTC 或比赛网络。浏览器播放地址不一定是可直接解码的视频流；WebRTC 等需确定网关方案。协议、编解码器、上游缓存及网络丢包要在真实设备上验证。
- FFmpeg 打开/读取超时由后端支持，采用打开时传入的参数；若平台后端无视超时，`stop()` 会报告未退出，不会无限新增读流线程。生产部署可进一步采用进程隔离来保证强制退出。

OpenCV 参数依据：[Video I/O properties 官方文档](https://docs.opencv.org/4.x/d4/d15/group__videoio__flags__base.html)。当前环境 OpenCV 4.10.0；本机网络解码已实测。尚无赛场数据，不能给出真实准确率或最终参数。
